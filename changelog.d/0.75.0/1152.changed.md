- **An explicitly requested FP8 that fails past the hardware gate now stops the run, and SFT's audio, unsloth and layer-streaming branches no longer accept FP8 without applying it (#1152 by @Srinivasan8888 in #PENDING).**
  On a card that can run FP8 with torchao installed, three failures used to
  become a yellow line and a bf16 run: `quantization_aware: fp8` whose float8
  conversion failed (the line blamed a missing torchao, which was false),
  `fp8_attention` whose attention pass failed partway (training continued on the
  half-converted model), and `fp8_attention` on a model with no attention
  projections (training continued as the no-op the converter had refused). Each
  now ends the run at setup with the converter's reason. SFT's audio setup
  (`modality: audio`) now applies FP8 after its LoRA attach, as the vision path
  does; it used to accept the setting and never call the converter. `backend:
  unsloth` and `training.stream_layers: true` are refused at config load with
  `quantization_aware: fp8` or `fp8_attention: true`, naming the setting and why
  (unsloth loads through its own path and never reaches the converter; streamed
  layers live on a meta skeleton and are never converted). No shipped recipe
  sets FP8 on either. A config that does not ask for FP8 is unaffected, and
  `nvfp4` still degrades to an advisory as before.
